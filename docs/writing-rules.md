# 記事を書く前に読むルール（きょうのこ）

**このファイルが存在しなかったせいで、1,109本の記事に同じ構造の誤りが入った。**
2026-08-19〜23の全面監査で出てきた実測をもとに、二度と同じことが起きないための規約をここに置く。

新しい記事を書くとき・既存記事を書き換えるときは、着手前にここを読むこと。
あわせて `docs/experiments-active.md`（進行中のSEO実験と凍結記事）も必ず見ること。

## 1. 体験談（`## 我が家のリアル`）に事実の断定を書かない

**書かないもの**: 金額 / 階数 / 貸出の有無 / 営業時間・休館日 / 台数 / 対象年齢の断定

これらは**本文の公式情報セクションが持つ**。体験談は体験に徹する。

  ❌ 「9階の授乳室が近くて助かった」
  ⭕ 「授乳室が同じ階にあって助かった」

**なぜ**: 2026-08-23の実測で、体験談に混入していた事実の**8割が「本文の公式セクションに既に
正しく書いてある事実の再掲」**だった。親切心で添えた数字が、公式の更新時に取り残されて古くなる。
サイト全体468本の体験談のうち**99本**がこの状態で、修正に丸1日かかった。

**実際に起きた事故**:
- モーニング3本で、体験談が4歳児のドリンクバーに198円を計上。**同じ記事の公式表は「未就学児無料」**
- 鴨川シーワールドで「入園9,600円」。記事の設定と本文の料金から計算すると**6,600円にしかならない**
- 上野動物園で「レンタル200円」。**自社の別記事は既に「200円ではありません」と書いていた**

**体験の節は、記録のある実訪問だけに置く（2026-10-11 社長方針で改定）。**
以前はここに「体験談そのものは資産なので消さない」と書いていた。2026-10-11 の全数監査で、
体験の節を持つ 691 本のうち 661 本に、節の内容を裏づける記録が見つからなかった
（582 本は 10 本以上を一度に追加した便で、雛形の「## 我が家のリアル／体験談 300〜500字」の枠に生成された文）。
記録が無いことは、事実でないことを意味しない。だが、読者にも取引先にも「いつ・どこで」を示せない
体験を、事実として載せ続けることはできない。

- **新しく書くとき**: 体験の節（我が家のリアル・うちの場合・体験談・体験メモ・編集部の失敗談 など）と、
  書き手の家族を主語にした文は、記録がある訪問についてだけ書く。記録が無ければ、節そのものを置かない
  （「体験していません」と空欄を作る必要もない）。
- **記録の置き場**:
  1. スポットの訪問 → `lib/kid-reports.ts`
  2. チェーンの店舗で確かめたこと（離乳食・温め・お湯・椅子・ベビーカー） → `lib/chain-reports.ts`
  3. 上の 2 つに入らない体験（注文・席・待ち時間・料金の支払いなど。社長の実体験で、置き場が無かったもの）
     → `data/experience-claims-baseline.json` の `records` に、記事・節の見出し・店舗（施設）・年月・
     確かめ方を書く。年月が分からなければ「不明」と書く（創作しない）。
- **書き方**: 節の見出しか本文に、記録の店舗名・スポット名と年月を書く
  （「## 編集長が草加店で確認したこと（2025年3月）」）。検査は、節の中に記録の名前があるときだけ通す。
- **すでにある体験の節**: 記録が無いものは「記録なし・確認待ち」として一覧（上の JSON の `entries`）に載っていて、
  扱いは 3 つに分かれる。**事実確認**（社長に確かめる・記録と照らす）／**修正**（一人称・利用頻度・金額を外し、
  公式で確かめられる事実だけ残す）／**節の削除**。一覧に載っている記事を、便の順番を待たずに勝手に消さない
  （凍結中・実験中の記事がある）。体験が事実だと分かったら、消さずに記録を登録する。
- 公式が書けない情報（「朝はほとんど乗らなかったのに、昼を過ぎて借りておいてよかったに変わった」等）は、
  記録のある訪問の節では、いままでどおり価値がある。削るのは検証可能な断定（上の「書かないもの」）。

**医療・安全は特に厳しく。** 「38.5℃で救急に行った」という体験は書いてよいが、
**「38.5℃を超えたら救急へ」という一般化した断定は体験談に置かない**（本文の免責つきセクションへ）。
`/editorial-policy` の「医療・健康は『医師・かかりつけ医にご相談ください』の免責を必ず付与」を割らない。

## 2. 施設を書く前に、実在を一次情報で確認する

2026-07に室内遊び場31本で**掲載施設の3〜5割が架空・閉店**、2026-08に水遊び記事で
**台東5/5・大阪5/6・品川4/5**が不良だった。実在しない公園・商業施設・店名を載せていた。

**確認の順序**:
1. **自治体のオープンデータ／GIS**で固有名を全数照合する（市の公園マップがArcGISなら
   REST APIを直接叩く。船橋で1,567フィーチャ・固有名997件を取得できた）
2. 無ければオープンデータCSV → 公式の一覧ページを全ページ取得
3. **運営元公式の店舗一覧**（チェーン店の場合）

**陽性対照を必ず取る。**「データに載っていない＝存在しない」と短絡しないため、
**同じデータソースが同種の対象を現に記録していること**を毎回確かめる。

  ⚠️ **東京都のオープンデータCSVは `備考` 列が全区で空**。大阪市の都市公園一覧xlsxも設備欄なし。
     **どちらも実在と住所の照合にしか使えず、設備の在否は証明できない**（各自治体の個別告知ページで見る）

**確認できない施設は、数を埋めるために残さない。本数より正確さが勝つ。**
船橋は6選→4選、吉祥寺は10選→6選、表参道は10選→5選に減らした。
**外した施設は「この記事から外した◯◯（公式に確認できなかったもの）」節で読者に説明する**
（その名前で検索して来た読者に「無い」と答えられる）。

## 3. 「エリアに複数店舗あり」と書かない

2026-08-22の実測で、駅別ランチ5本のうち**5本すべてでハズレ**だった。
丸亀製麺は吉祥寺にも池袋駅前にもなく、サイゼリヤは渋谷道玄坂にも表参道にもない。

**チェーン名＋エリア名から店舗の存在を推定しない。公式店舗検索で引いてから書く。**

再利用できる公式データ源（2026-08-22に確立・いずれもcurlで取れる）:

  モスバーガー  https://www.mos.jp/data/shop/shop.json （全国・市区町村コードで絞る）
  コメダ        https://eu.komeda.co.jp/v1/hp/shop?prefecture=東京都&brand_type=1
  丸亀製麺      https://stores.marugame.com/sitemap1.xml → 個別店舗ページ（全店の店名・所在地を全数照合できる）
  サイゼリヤ    https://shop.saizeriya.co.jp/sz_restaurant/spot/list?address=… （「検索結果：N件」で完全列挙）
  丸井          https://www.0101.co.jp/contents2/facilityinfo/<店番>/facility.json
  すかいらーく系 https://store-info.skylark.co.jp/api/point/{5桁geohash}/ （セル単位で全ブランド全店が返る。
                大井町は xn76e。ガスト/ジョナサン/バーミヤン/しゃぶ葉の在否を1リクエストで確認できる）
  ゼンショー系   maps.sukiya.jp / maps.hama-sushi.co.jp / maps.cocos-jpn.co.jp / maps.nakau.co.jp
                `…/jp/address.html?q=東京都◯◯区` で区ごとに全数照合できる
  b-map系      吉野家/ドトール/松屋/ロイヤルグループ/やよい軒は api/proxy2/shop/list?address=13109 型（区コード指定）。
                `?coord=緯度,経度&radius=1200&limit=100` の半径検索も使える
  マクドナルド  https://map.mcdonalds.co.jp/sitemap.xml で店舗コードを列挙 → /map/{code} を取得
                （個別ページはJS描画なのでsitemap経由が確実。設備アイコンはJSで一律出力＝各店の判定には使えない）
  スターバックス 検索APIは403だが `https://store.starbucks.co.jp/pref/tokyo/?city=◯◯区` と
                店舗詳細 `/detail-{id}/` は素のcurlで取れる
  CoCo壱番屋    https://tenpo.ichibanya.co.jp/api/point/ が**全国1,231店を無認証で一括返却**（座標・営業時間・座席数つき）
  KFC          https://search.kfc.co.jp/points/{id}
  レインズ系    https://map.reins.co.jp/{gyukaku|onyasai}/tokyo のHTMLに data-lat / data-lon / data-store(JSON) が全店分。
                くら寿司 shop.kurasushi.co.jp/tokyo も同じCanly系で同構造
  Canly新版     大戸屋 store.ootoya.com は一覧に件数しか無いが、詳細 `/detail/{storeId}/` に全データが入る

  ⚠️ 旧記載「ガスト・すかいらーく系は機械的に引けない」は**2026-08-31に反転**。旧 store.skylark.co.jp の
     話で、新ロケータ store-info.skylark.co.jp の point API で引ける（大井町の全数確認で実証済み）。
  ⚠️ 「無い」判定には**陽性対照**を必ず取る（同じAPIで別エリアの実在店が引けることを確認してから0件と書く）
  ⚠️ **b-map/NAVITIME系が返す緯度経度は数百m狂うことがある**（2026-09-01に神田エリアで実測。松屋 神田南口店は
     住所が千代田区鍛冶町2-1-2なのに座標は本石町付近＝三越前から136mを指した）。
     **距離の判定は座標を鵜呑みにせず、必ず住所の丁目で裏取りする。**
  ⚠️ **同じチェーンでも店舗ごとに条件が違う**。ベビーカー貸出の対象月齢は北千住マルイ＝生後10ヶ月〜2歳、
     錦糸町マルイ＝生後1ヵ月〜4才。「マルイなら借りられる」と一般化しない。

## 4. 「公式に記載がない」を「ある」とも「ない」とも書かない

確認できなかったものは **「公式に記載を確認できませんでした」** と書き、確認先（公式URL・電話）を案内する。

**数字を直せないなら、数字ごと削除して確認導線に置き換える**（2026-08-20にバーミヤンで採った方法）。
推測で新しい数字を書くのは、直している誤りを新たに作るのと同じ。

### 「掲載なし」「確認できませんでした」と書く前に見る4か所

**見た場所に無かっただけのものを「公式に掲載なし」と書かない。** 実在するメニュー・店舗を「無い」と書いた事故が2回ある
（2026-08-31 大井町「駅前にサイゼなし」→公式ロケータに実在／2026-09-04 丸亀製麺・大戸屋「公式にキッズメニューの掲載なし」→どちらも掲載あり。
2026-10-01に訂正。丸亀は28日で1.2万表示の記事が公式と逆の答えを出していた）。

メニュー・商品について「無い」「確認できない」と書くのは、次の4か所を全部見てからにする。

1. **JSで描画されるメニュー一覧を実ブラウザで開く。** 丸亀製麺のうどんメニューは curl では商品名が1件も出ないが、
   ブラウザでは「お子さま まんぷくセット」が並んでいる。
2. **キャンペーン・特設ページ**（`/campaign/` など）。丸亀のセットは特設ページが正で、文言は画像の alt に入っている。
3. **店舗別メニュー。** 大戸屋は「店舗を選ぶとメニューが表示される」仕組みで、トップのメニュー一覧には何も出ない。
   2〜3店舗を選んで中を見る（`menu_list/index/{店舗ID}`）。
4. **自社の他の記事を grep する。** 9/04の一括確認は、8/31に `kids-menu-chain-15-hikaku` が公式URLつきで書いていた
   「大戸屋はキッズメニューあり」を上書きして「掲載なし」にした。既存記事と逆の結論になったら、どちらかが誤り。

4か所を見ても無ければ「公式サイトのメニュー一覧・特設ページ・店舗別メニュー（◯◯店）に記載を確認できませんでした」と、
**見た場所を書く**。「公式に掲載なし」と範囲を広げて書かない。

## 5. 動的描画のページでも数字は取れる

「JavaScriptだから確認できない」と諦める前に、**そのページ自身が読んでいるデータ**を探す。

  ピューロランドの料金      公式が読む一次JSON `common_v2/json/YYYYMM.json` に日別の価格帯・開園時刻
  しながわ水族館の休館日    JSの `addClass('close')` にべた書き
  鴨川シーワールドの料金    **旧料金表がHTMLコメント `<!-- -->` の内側**に残っていて、素で抜くと混ざる

curlがbot遮断される場合（ディズニー公式など）は、**ブラウザ自動操作**（`mcp__Claude_Browser__*`）を使う。
読み取りのみ。CAPTCHAが出たら突破せず中止する。

## 6. 期限のある情報には「賞味期限」を書く

会期・休止・キャンペーンは必ず終わる。**記事に期限を明示し、読者が自分で最新を確認できるURLを置く。**

  例: 東京ディズニーシーのベビーセンターは 2026年5月12日〜10月2日 休止
      → 各記事に「この記事の賞味期限：2026年10月2日」節＋公式URL、
        あわせて期限日に更新タスクを予約した

**タイトルに日付を入れたら、必ず更新タスクを予約する**（放置すると最も目立つ形で誤情報になる）。

## 7. 書き終わったら4つのガードを通す

```bash
node scripts/check-fabricated-claims.mjs     # 記録の確認が要る書き方（§9。既知の一覧に無いものだけ exit 1）
node scripts/check-cross-article-facts.mjs   # 監査済み記事との食い違い（ERRORは0を維持）
node scripts/check-parking-claims.mjs        # 駐車場の断定に営業時間があるか
node scripts/check-internal-links.mjs        # 内部リンク切れ
```

`check-cross-article-facts.mjs` は**同じ施設について記事間で食い違っていないか**を見る。
「監査済み」の判定は**本文中の確認日**（`updatedAt` は一括加工でも動くので一次情報を当たった証拠にならない）。

  ⚠️ **「監査済みの記事だから正しい」とは限らない。** 2026-08-22に、監査済み2記事が
     「昭和記念公園は立川駅から徒歩15分」で一致していたが、**公式はゲートごとに違い**
     （あけぼの口10分／立川ゲート18分／西立川ゲート2分）、どちらも不正確だった

## 8. 出典の書き方

確認した項目には**出典URLと確認日**を添える。記事末尾に `## 出典` 節を置くのが標準。

  > 出典：東京都公園協会「舎人公園」公式サイトの駐車場欄
  > （https://www.tokyo-park.or.jp/park/toneri/ ）｜確認日 2026年8月20日

**引用した公式URLは、貼る前にcurlして200を確認する**（リンク切れの出典は出典ではない）。

## 9. 点数・順位・利用比率は、記録が無ければ書かない

2026-10-10、`conveni-kodzure-kids-shokuzai-4sha` に「5軸×10点=50点満点」の採点、1〜4位の順位、
「我が家の利用比率 セブン4：ローソン3：ファミマ2：ミニストップ1」が、記録なしで載っているのが見つかった。
点数は記事の生成と同時に置かれた値で、いつ・どの店で・どう数えたかの記録はどこにも無かった。
同じ型（N社×5軸×10点）は公開中に12本あり、ほかの記事がその順位を「総合1位です」と引いていた。

**書かないもの**（記録が無いとき）:

  ❌ 「5軸×10点=50点満点で採点」「43/50」「1位 セブン-イレブン」「総合ランキング表」
  ❌ 「我が家の利用比率は 4：3：2：1」「延べ100店舗」「月2〜3回利用」「5年やってきた」
  ❌ 「ママ50人にきいた」「先輩ママ150人の声から」（聞いた記録が無い調査の体裁）
  ❌ ほかの記事の採点を引いて「◯◯は総合1位です」

**代わりに書くもの**:

  ⭕ 公式で確認できる事実の比較表（確認日と出典つき。確認できない項目は「公式に記載なし」）
  ⭕ 公的機関が年齢で線を引いている注意（消費者庁・厚生労働省など。URLと公表日つき）
  ⭕ 順位や点数を外したときは「## この記事から外したもの」節で、何を・なぜ外したかを読者に説明する

2026-10-11 に足した型（どれも、記録が無ければ書かない）:

  ❌ 「公開の口コミ約150件の声を傾向分析」「〜という声が約78%」「編集部に届いた声（約150件集計）」
     （題・説明文に書いても同じ。公式の店舗検索の全件集計のように、数え方と出典を書いたものは別）
  ❌ 「Aさん（30代・1歳児）：『…』」（だれの発言かを確かめられない引用）
  ❌ 「年間100回以上通って」「首都圏30店舗以上を実地確認」「複数店舗を利用してきた」
  ❌ 「◯◯区在住の友人ファミリーに同行した日」

一人称の体験（体験の節・我が家・うちでは・実体験 等）は、記録がある訪問についてだけ書く（§1）。

### 検査（どこで・何が止まるか）

規則の定義は `lib/claim-rules.mjs` の 1 か所で、次の 4 つが同じものを読む。

| どこで | 何をするか |
|---|---|
| PR（`.github/workflows/claims-check.yml`） | 記事・規則・既知の一覧・記録を変える PR で `node scripts/check-fabricated-claims.mjs` を実行。**既知の一覧に無い記事×型、または既知の記事で件数が増えたときだけ失敗**。本番のビルド（prebuild）には入れていない（既知の分や期限切れで本番の反映が止まる事故を避けるため） |
| `npm run publish` | 対象の slug に同じ検査を当て、新しい混入があれば本番に出す前に止める |
| 管理画面の保存（`/api/admin/edit-content`） | 保存する本文に、**前の版に無かった**該当の書き方があると保存を止め、一覧を出して確認を求める。記録がある事実だと確認して保存したものは、サーバーのログに `[claims] confirmed save` と残る |
| 法人営業の送信前（`scripts/tieup-preflight.mjs`） | §10 |

失敗になる型: 点数／順位／比率・回数・年数・店舗数／調査の体裁／集計の体裁／名前を伏せた他人の声／
体験の節の見出し／書き手の家族を主語にした文。
警告にとどまる型: 「実際に食べる」「助けられた」「うちの子」のように体験とも一般論とも読める言い回し、
題の「ランキング／TOP」、「公式が〜と案内」。

既知の一覧は 2 つ。どちらも、**載っている行は「記録なし・確認待ち」の意味で、事実でないと決めたものではない。**

- `data/unfounded-claims-baseline.json` … 点数・順位・比率・調査・集計・他人の声（記事×型・期限つき）
- `data/experience-claims-baseline.json` … 体験の節・一人称の文（記事ごと。扱い＝事実確認／修正／節の削除、便、期限、件数 n）

直したら行を消す（体験の一覧は `node scripts/check-fabricated-claims.mjs --tighten` で、件数を現状まで下げ、
当たらなくなった行を消す）。読んで誤検知と決めたものは `ignore` に理由つきで書く。
一覧に行を足すのは「見逃しの追認」なので、理由を書く。

管理画面で保存した本文（KV の上書き）をまとめて見るとき:
`node scripts/kv-article-overrides.mjs --dump --out=<フォルダ>` で書き出し、`node scripts/check-fabricated-claims.mjs --dir=<フォルダ>` で見る。

## 10. 法人営業で相手に見せる記事は、送る前に監査する

メールや資料に URL を載せる記事は、下書きを作る前と送信の前に
`node scripts/tieup-preflight.mjs <URL か slug> …`（機械で読むときは `--json`）を実行する。
`origin/main` の本文に §9 と同じ規則を当て、記事ごとに「送ってよい／確認が要る」と、該当の抜粋（先頭 3 件）、
凍結中かどうか、更新日を出す。**確認が要る記事・検査できない URL（記事以外のページ・見つからない slug）が
1 本でもあれば exit 1** で、その先の下書き・送信は作らない。全記事の検査とちがい、既知の一覧に載っている
記事も「確認が要る」になる（相手に見せてよいかは、直す予定の有無と関係がない）。
この監査が見ないもの: 価格・対象年齢・営業時間が公式の最新と合っているか（更新日が 30 日より前の記事には
印が付く）、管理画面で保存した本文（`node scripts/kv-article-overrides.mjs --list --only=<slug>` で見る）、
記事以外のページ。「確認が要る」は記録を人が確かめる必要があるという意味で、事実でないと決めるものではない。
