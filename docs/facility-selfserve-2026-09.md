# 施設セルフサーブ構想（施設側が無料会員登録し、自分でページを編集する）

作成: 2026-09-15
関連: `docs/strategy-2026-09.md`（研究機関化・PV戦略）/ `docs/sales-outreach-plan.md`（写真提供型の営業）/ `app/for-facilities/page.tsx`

---

## 0. 結論（先に読む3行）

1. **この構想は既存戦略と競合しない。** `docs/sales-outreach-plan.md` §2 が「いずれ施設側から載せてほしいと言ってくる」と書いた状態を、仕組みで前倒しするもの。方向は正しい。
2. **ただし順序を逆にすると死ぬ。** 「マイページを作る → 施設が集まる」ではなく、**「施設ページに一次情報が乗る → 条件検索の面が厚くなる → 流入が出る → 施設が集まる → 課金できる」**。マイページは2番目の工程にすぎない。
3. **最初に作るべきものはマイページではなく、施設ページからの導線（claim ボタン）とフォーム受付。** コードは数十行。これで需要を実測してから、認証・マイページ・課金に進む。

## 1. 「施設が全然表示されていない」の正体（2026-09-15 リポジトリ実測）

課題認識は正しい。ただし原因は「掲載数が足りない」ではない。**ページはもうある。中身が空で、入口が無い。**

### 実測値

| 項目 | 実数 | 出所 |
|---|---:|---|
| 施設（スポット）ページ総数 | **820** | `getAllSpotsWithSlug()` |
| うち indexable | **791（96.5%）** | `isSpotIndexable()` |
| **画像がある施設** | **153（18.7%）** | `spot.images` / `spot.image` |
| **住所がある施設** | **0** | `Spot` 型に `address` フィールドが存在しない |
| **営業時間がある施設** | **0** | 同上。`hours` フィールドも無い |
| **電話番号がある施設** | **0** | 同上 |
| 構造化データの住所精度 | **区市町村のみ**（`addressLocality`） | `lib/spot-schema.ts` L19, L284-287 |
| 施設ページから `/for-facilities` への導線 | **0箇所**（フッターのみ） | `grep -rn "for-facilities" app components lib` |

### これが意味すること

**A. 施設ページはローカル検索の勝負にそもそも参加していない。**
施設名で検索する人が欲しいのは「行き方・営業時間・料金・写真」。その全部を、公式サイト・Google マップ・いこーよ・じゃらん・食べログは持っていて、きょうのこは**一つも持っていない**。住所も営業時間も電話も無い `LocalBusiness` が pos 8〜9 で止まるのは構造的な帰結で、タイトル調整では動かない。

> `lib/spots.ts` の冒頭コメント: 「住所・電話番号は意図的に持たない（変更リスクがあるため）」
> — **この判断自体は当時正しい。**個人運営で820施設の住所と営業時間の鮮度を保証するのは不可能だから。
> だが同時に、これが施設ページが弱い**最大の単一要因**でもある。

**B. だから、この構想の本当の価値は「営業が要らなくなる」ではなく「今まで持てなかったデータを持てるようになる」こと。**
施設本人が更新するなら、鮮度は施設が担保する。**ポリシーを破らずに住所・営業時間・写真を持てる唯一の方法がこれ。** ここを構想の中心に据える。副次的な効果ではなく、これが主目的。

**C. 施設が「自分のページがある」ことに気づく導線が存在しない。**
820ページあって、施設向け案内へのリンクはフッターの1本だけ。施設の担当者が自分の施設ページを見ても、修正を申し出る方法が画面上に無い。**これは今日直せる。**

### 未検証（要ローカル実行）

`/spot/*` の GSC 実数（imp・CTR・順位の分布）は、このクラウドセッションに GSC の鍵が無いため取れていない。着手前に必ず出す:

```bash
node scripts/gsc-report.mjs --days=90 --json=/tmp/gsc.json   # ローカル（credentials/google-indexing.json）
# /spot/ で絞って imp 上位50・CTR・平均順位を出す → Phase 0 の営業先リストと go/no-go 判定に使う
```

判定基準:
- `/spot/*` に **imp が出ている（合計1万/月以上）** → CTR と情報量の問題。この構想が効く
- **imp 自体がほぼ無い** → 情報量以前に順位が付いていない。施設ページ単体を伸ばす路線は捨て、**一覧面（条件×エリア）に施設データを流す設計に寄せる**（§4 Phase 2 が主戦場になる）

参考: `docs/strategy-2026-09.md` §11 の「やらないこと」に **「スポット・駅×条件ページの拡張 / 4,700ページで検索流入ほぼゼロ」** と既に書かれている。`reports/rank-pushup-2026-08-27.md` L157 では `/spot/-irhu` が 1,578imp / pos 8.2。**imp は出るがクリックにならない**状態。

⚠️ この構想は、その「やらないこと」を**覆すものではない**。「中身が空のスポットページを増やすな」は今も正しい。変えるのは**ページ数ではなく1ページの中身**で、しかも中身を入れる人件費を施設側に移す。ここを混同すると、また4,700ページの薄いページを作ることになる。

## 2. 技術基盤は7割できている

新規開発として見ると大きいが、実際は**既にあるものの組み替え**が大半。

| 必要なもの | 現状 | 追加作業 |
|---|---|---|
| 施設単位のデータ上書き層 | **ある。** `lib/spot-overrides.ts` — slug をキーに任意フィールドを KV で上書き。slug は不変なので編集で URL が変わらない設計 | 「運営者 override」と「施設 override」の**レイヤー分離** |

| 編集 UI | **ある。** `/admin/spots/edit`（`SpotsEditClient.tsx`） | 施設向けに項目を絞った版 |
| 投稿の承認フロー | **ある。** 口コミが Turnstile → サーバ検証 → レート制限 → **承認制** で `/admin/reviews` 承認（`app/api/reviews/route.ts`） | 同じ型を施設編集に流用 |
| 施設向け案内ページ | **ある。** `/for-facilities`（写真提供の依頼） | claim の入口に書き換え |
| 営業リスト | **ある。** `docs/outreach-full-688.csv`（847行）・`outreach-pilot-30.csv`・`sales-deck-phase1.md` | オファーを「写真ください」→「編集権を渡します」に差し替え |
| **施設アカウント認証** | **無い** | Auth.js の Email magic link |
| **オーナー確認（誰がこの施設の人か）** | **無い** | §4 Phase 1 |
| **課金** | **無い**（Stripe MCP は未認証。接続が必要） | Stripe Checkout + Customer Portal + webhook |
| **`Spot` 型の住所・営業時間・電話** | **無い** | 出典（`operator`/`facility`/`official`）と確認日つきで追加 |

**結論: 認証・オーナー確認・課金の3つが新規。それ以外は既存資産の再利用で足りる。**

## 3. 何を売るのか（ここを間違えると詰む）

### 売ってはいけないもの

| ✕ | 理由 |
|---|---|
| 「検索順位を上げます」 | 提供できない。売った瞬間に編集の独立性が死ぬ（`/business` に明記した方針と矛盾する） |
| 「集客できます」 | 現時点の施設ページは流入ほぼゼロ。**嘘になる。**一度言うと信用が戻らない |
| 有料施設を無表示ラベルで一覧上位に出す | 景表法・ステマ規制違反。`PR` 表記が必須 |

### 売れるもの（PV が小さいうちでも成立する順）

1. **問い合わせ削減** — 「離乳食の持ち込みは可能ですか」「授乳室は何階ですか」「ベビーチェアにベルトはありますか」。実測で分かっているとおり**公式サイトにはほぼ書かれていない**（`docs/strategy-2026-09.md` ①-2: 授乳室・取り分け・ベビーカーは公式記載ほぼなし）。施設側も「聞かれるのに書く場所がない」。これは**PV と無関係に価値がある**。
2. **無料で、即日、自分で直せる** — いこーよ・食べログは掲載自体が交渉か有料。無料で編集権が手に入るのは訴求になる。
3. **子連れ条件での露出** — きょうのこが実際に勝っているのは「キッズメニュー」「子連れ 攻略」等の**条件クエリ**。施設名クエリではない。だから売り物は「施設名で1位」ではなく**「その条件で探している親に見つかる」**。
4. **実訪問取材つきタイアップ**（既に `/business` で運用中の型・¥50,000〜）— 今この瞬間いちばん確実に現金化できるのはこれ。セルフサーブが育つまでの収益はここで受ける。

### 料金の叩き台（Phase 3 で確定させる）

| プラン | 月額 | 含むもの |
|---|---:|---|
| 無料 | ¥0 | 情報修正・写真3枚・設備情報・営業情報・公式リンク・「施設提供（確認日）」バッジ |
| スタンダード | ¥1,980 | 写真10枚＋動画、お知らせ投稿（季節メニュー・イベント）、クーポン、計測付き公式/予約リンク、**月次レポート**（自施設が条件別一覧で何回表示され何回クリックされたか＝サイト内実測。GSC ではない） |
| プレミアム | ¥9,800 | 上記＋一覧内 **PR枠**（ラベル必須）、特集への優先掲載、記事内の施設カード、Instagram/LINE 配信1回 |
| スポット | ¥50,000〜 | 実訪問取材タイアップ記事（`/business` の既存メニュー） |

**無料プランが薄いと有料は売れない。** 無料で「ここに載っていると助かる」状態を作るのが先。

## 4. 実装フェーズ（各フェーズに go/no-go を置く）

### Phase 0 — 導線と受付だけ作る（1〜2週間・認証なし・コードほぼ書かない）

**いちばん重要なフェーズ。ここを飛ばしてマイページを作ると、誰も来ないマイページができる。**

| # | やること | 実装箇所 |
|---|---|---|
| 0-1 | 施設ページに常設の導線を置く。「**施設の方へ：情報の修正・写真の掲載（無料）**」 | `app/spot/[slug]/page.tsx`（slug をクエリで `/for-facilities` に渡す） |
| 0-2 | `/for-facilities` を「写真ください」から「**このページはあなたの施設です。無料で編集権をお渡しします**」に書き換える | `app/for-facilities/page.tsx` |
| 0-3 | 申請フォームを作る（施設名・掲載URL・担当者名・**公式ドメインのメール**・修正したい内容・写真）。受付は KV に積むだけ。反映は**人力** | `/api/facility-claim`（口コミ API の Turnstile＋レート制限をそのまま流用） |
| 0-4 | 申請一覧と反映を admin に生やす（既存の override 編集画面に繋ぐだけ） | `app/admin/` に1画面 |

**設計上の最重要判断: 「新規登録」ではなく「claim（このページは私の施設です）」にする。**
820ページはもう存在する。Google ビジネスプロフィールと同じ型。ゼロから登録フォームを書かせる設計にすると誰も来ない。`docs/sales-outreach-plan.md` のコアメッセージ（「貴施設のページ、もう公開しています」）がそのまま使える。

**go/no-go: 1か月で claim 申請が 5件未満なら Phase 1 に進まない。**
「営業しなくても来る」はいこーよの規模で初めて成立する。きょうのこには施設側の認知がまだ無い。ここで実数を見る。0件だったときにマイページを作っていないのが、このフェーズの最大の価値。

**Phase 0 と並行して打つ営業（一回だけやる。これは避けられない）**
- GSC で `/spot/*` の imp 上位50を出し、**「もう表示されている」施設**から声をかける（損失回避が効く）
- `docs/outreach-full-688.csv` の★★★を使い、オファーを「写真ください」→「無料で編集権をお渡しします」に差し替える

### Phase 1 — アカウントとマイページ（無料のみ・4〜6週間）

Phase 0 で需要が確認できてから着手。

**1-1. 認証**
- Auth.js の **Email magic link**。パスワードを持たない（個人運営でパスワードリセットと漏洩対応を抱えない）
- セッションは施設アカウント専用。既存の一般ユーザー（お気に入り・設定は localStorage）とは混ぜない

**1-2. オーナー確認（ここを甘くすると乗っ取られる）**

| 方法 | 判定 |
|---|---|
| 公式サイトに記載のドメインのメールアドレス（`@motherfarm.co.jp` 等）で受信確認 | **自動承認** |
| 公式サイトに確認用ファイル/メタタグを設置（Search Console 方式） | 自動承認 |
| フリーメール | **手動審査**。公式サイト記載の窓口へこちらから確認を取る |

`lib/spot-official-urls.ts` に公式URLが既にあるので、ドメイン照合は自動化できる。

**1-3. 編集できる範囲（構想の成否を分ける線引き）**

| 施設が編集できる | 施設が編集できない |
|---|---|
| 住所・営業時間・定休日・電話・公式URL | **記事本文** |
| 料金（大人/小学生/幼児/乳児） | **運営者の実訪問レポート**（`lib/kid-reports.ts`） |
| 設備（授乳室・おむつ台・ベビーチェア・離乳食持込・ベビーカー・キッズスペース・駐車場） | **口コミと評価** |
| 写真（プラン枚数まで）・お知らせ・クーポン | **ランキング順位・比較表の評価** |

`/business` に明記した「編集権は媒体側が持つ」方針と整合させる。**ここを曖昧にすると媒体の信頼が死ぬ**ので、施設向け利用規約に同じ線を書く。

**1-4. 反映のしかた**

- 設備の yes/no・営業情報・料金 → **自動反映**＋「**施設提供（2026-09-15 確認）**」バッジ
- 自由文・写真 → **承認キュー**（口コミの承認フローを流用）
- 出典レイヤーの優先順位: **運営者の実訪問 > 施設提供 > 元データ**
  - `lib/spot-overrides.ts` を**運営者レイヤーと施設レイヤーに分ける**。混ぜると出典が追えなくなり、`check-fabricated-claims.mjs` 系の監査が壊れる

**1-5. `Spot` 型の拡張（この構想の技術的な本体）**

```ts
// 出典と確認日を必ず持たせる。これが無いと「鮮度を担保しない」ポリシーを破ることになる
type SourcedField<T> = { value: T; source: 'operator' | 'facility' | 'official'; verifiedAt: string };

address?:      SourcedField<string>;   // streetAddress まで
hours?:        SourcedField<string>;   // openingHoursSpecification に変換
closedDays?:   SourcedField<string>;
tel?:          SourcedField<string>;
officialUrl?:  SourcedField<string>;
```

- `lib/spot-schema.ts` を `LocalBusiness` フルセットへ（`streetAddress` / `openingHoursSpecification` / `telephone` / 複数 `image`）
- **未確認の項目は出さない。** 推測日を入れない（既存 `SpotVerification` の設計方針を踏襲）

**go/no-go: claim した施設の 50% 以上が実際に1項目以上編集を完了するか。** 完了しないならマイページの UX が重すぎる。

### Phase 2 — 集まったデータを流入に変える（Phase 1 と並行・これが本当の主戦場）

**ここを作らないと課金に進めない。**施設が増えても流入が増えなければ、翌月に解約される。

| # | やること |
|---|---|
| 2-1 | **条件×エリアの一覧面を実データで開く。**「授乳室あり × 渋谷区」「離乳食持ち込みOK × 横浜」等。施設提供データが閾値（例: 該当施設10件）を超えた条件から順に開く |
| 2-2 | 流入の受け皿は**一覧面**、施設ページはそこからの内部遷移で受ける。施設ページ単体のSEOに賭けない（§1-A の構造的理由） |
| 2-3 | PV/セッション 1.26 → 1.5 を狙う。一覧 → 施設 → 近隣施設の回遊で稼ぐ（`docs/strategy-2026-09.md` §3 の式の第4項） |
| 2-4 | `#228` の型（駅ページからの内部リンク＋タイトルに検索語彙を併記）を施設ページに適用 |

⚠️ 2-1 は §11 の「スポット・駅×条件ページの拡張はやらない」に**見た目が似ている**。違いは、**中身が空のページを機械生成するのではなく、施設提供の実データが揃った条件だけ開く**こと。既存の3条件（GSC で需要確認）を必ず通す。**需要未確認のセルは作らない。**

**go/no-go: 施設ページの CTR（現状ほぼゼロ）と条件一覧面の検索クリック。** ここが動かないなら Phase 3 の課金は延期する（売るものが無い）。

### Phase 3 — 課金（Phase 2 で流入が動いてから）

- Stripe Checkout（サブスク）＋ **Customer Portal**（解約・支払い方法変更は自作しない）
- webhook で KV/DB のプラン状態を更新。プラン判定は**サーバ側のみ**
- **Stripe MCP が未認証**。claude.ai のコネクタ設定で認証が必要（このセッションからは実行できない）
- 必要な法務対応:
  - 施設向け利用規約（編集権の線引き・掲載可否の最終判断は媒体側・写真の利用許諾範囲）
  - **特定商取引法に基づく表記**（有料課金を始める時点で必須）
  - **PR 表記**（有料枠は必ずラベル。景表法・ステマ規制）
  - 施設担当者の個人情報の取り扱い（既存プライバシーポリシーの改定）

**現実的な転換率: 無料100施設で有料2〜5件。** ¥1,980 × 3件 = 月¥6,000。**AdSense の月¥26,000 に届くのは無料300施設規模から。**課金を急いでも収益にならない。急ぐべきは無料施設数と Phase 2。

---

### Phase 4 — データ資産として既存戦略に合流

施設提供データは `docs/strategy-2026-09.md` §5-1 の調査ページの母数になる。
「**施設が自己申告した子連れ設備 vs 公式サイトに記載がある設備**」の二層比較は、**施設側データを持つ媒体でなければ作れない調査**。この構想は研究機関化路線の供給源になる（競合しない）。

## 5. スケジュールと本当のコスト

| 時期 | フェーズ | 週あたり工数の目安 |

| 2月以降 | Phase 3（課金） | 中 |

**最大のコストは開発工数ではなく機会費用。** Phase 1 の4〜6週間、`docs/strategy-2026-09.md` の「年内30万PV」に向けた①②③が止まる。現在 9.4万PV で、目標まで残り3.5か月。

**判断の分岐:**
- **年内30万PV を優先する** → Phase 0 だけ今やって（工数が小さく、実測データが取れる）、Phase 1 は1月以降
- **施設セルフサーブを本命に据える** → 年内PV目標を下方修正して明示的に降ろす。**両方を同時に追うと両方遅れる**

推奨は前者。**Phase 0 は今週やる価値がある**（安い・情報が増える・失敗しても損失が小さい）。Phase 1 の着手判断は、Phase 0 の申請件数と `/spot/*` の GSC 実数を見てから。

## 6. リスク

| リスク | 兆候 | 備え |
|---|---|---|
| **claim が来ない（最大リスク）** | Phase 0 の1か月で5件未満 | Phase 1 に進まない。営業リストの★★★30件に直接当てて反応を見る |
| 施設が書いた情報が誤っている | 施設提供データと公式記載の矛盾 | 出典レイヤー分離＋確認日表示＋「施設提供」バッジ。**アレルギーは施設提供でも公式リンク必須**（YMYL。§5-3 の方針を踏襲） |

| 既存戦略が止まる | 10月末の新規セルが100本未満 | §5 の分岐を明示的に選ぶ。無意識に両方追わない |
