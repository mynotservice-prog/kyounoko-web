# 駅×条件ページの作り直し（実在店・根拠つき）設計書

2026-10-28 作成。社長決定（2026-10-28）: 案A・B・Cを採用。追加方針「既存ページを一括削除しない／個人店を含めて実在店を増やす／1km案は実用的な距離で検討／件数が少なくても需要があれば作り直して残す／根拠のない店舗数・設備はすぐ直す」。本番公開はまだしない。

ページ別の試算: `reports/station-cond-rebuild-2026-10/pages.csv`（1,240面。GSC 直近90日の実績、800m・1kmの店数、提案、条件つき駅リンクを張る記事と凍結の有無）。

## 1. 何が起きているか

- 第3便（PR #304・10/28）で駅のチェーン一覧を、公式で実在を確認した店だけにした。条件ページの判定（`isStationConditionIndexable`）は「チェーン単位の手入力の値（`kidsMenu` や `privateRoom`、雨の日は説明文の「モール」「駅直結」）×一律付与のチェーン数」のままだったので、件数が3を切った面が配信対象から外れた。
- **配信対象が 1,468面 → 1,069面（399面減）**。306面は駅トップへ301、93面は404。消えた面の GSC 直近90日（7/28〜10/25・確定値）は **1,055クリック／21,891表示**。
- 消えた面の多くは、もともと実在しない店を載せていた。例: 東京駅のファミレスは旧ページで10件（一律付与）、実在は800m内2店・1km内4店。品川の雨の日の天丼てんや・洋麺屋五右衛門は800m内に店が無い。
- **いま配信中の面も同じ根拠で作られている**。店単位の根拠で数え直すと、配信中1,069面のうち315面（2,544クリック）が「実在チェーンだけでは3店未満」になる。消えた面だけを直しても、残っている面の誤りは残る。

## 2. 方針

1. **配信中のURLは1面も消さない。** 中身を「実在店×根拠」に入れ替える。店が少ない面も、需要がある限り URL を残して作り直す。
2. **件数・設備は根拠のあるものだけを数える・表示する。** 根拠の段は下の4つで、どれに基づくかをページに書く。
3. **消えた面は、実在店が見つかる面から戻す。** 需要（GSC の表示実績）がある面は、店が1〜2店でも「少数掲載型」で戻す。店が0の面は、まず試験で一部だけ戻す。
4. **品川の雨の日は301のまま**（社長決定）。雨の日は全駅とも、建物の公式台帳ができるまで判定を保留する。
5. 実験中の面（凍結記事）のリンク先を動かさない段取りにする（§7）。

## 3. 根拠の段（数えてよいもの）

| 段 | 何を | 使える条件 | 出典の表示 |
|---|---|---|---|
| 店の公式 | チェーン公式の店舗検索で、その店に表示がある設備（`VerifiedStore.fac`。全国集計 9/11〜9/25） | キッズメニュー（お子様メニュー・キッズセット）、0〜1歳（おむつ替え・子ども椅子・ベビーチェア・授乳スペース）、個室・座敷（座敷・小上がり・個室） | 「この店の公式ページにある設備」＋集計日 |
| ブランドの公式 | `lib/chain-facilities.ts` で `ok: true` かつ `scope: 'brand'`（全店向けの公式の記載）の項目 | キッズメニュー、0〜1歳（キッズチェア・おむつ替え台・離乳食持ち込み）、座敷 | 「チェーン公式（全店）」＋公式URL＋確認日。`partial`・`some-stores`・`unknown` は数えない |
| 業態 | 実在店のチェーンの業態（ファミレス・回転寿司・焼肉） | ファミレス・回転寿司・焼肉 | 業態は推測ではないので出典表示は不要。**しゃぶ葉・温野菜は「焼肉」に数えない**（しゃぶしゃぶ） |
| 店舗掲載（ホットペッパー） | 「お子様連れ歓迎・ランチあり」の個人店。ジャンル（焼肉・韓国）、個室「あり」、お子様連れ欄の店のコメント（椅子・ベビーカー・お子様メニュー等） | 焼肉、個室、0〜1歳、キッズメニュー、個人店 | 「ホットペッパーの店舗掲載情報（店の記載）」。店が書いた内容なので「公式」とは書かない |
| 建物の公式台帳（新設） | 建物・運営者の公式に「駅直結」「雨に濡れずに」等の記載があり、改札外で入れる建物 | 雨の日 | 建物公式の原文＋URL＋確認日（`gate-status.json` と同じ作り） |

数えないもの: `Chain` 型の手入力の値（`kidsMenu`・`babyChair`・`privateRoom`・`babyFoodOk`・`stroller`）、チェーンの説明文、駅の規模、チェーン共通の「目安」。

## 4. 距離

- 駅から**直線800m＝大人の徒歩約10分**。直線は実際の道より短く（概ね1.2〜1.3倍）、ベビーカーや子連れは分速60m前後なので、**直線1kmは子連れで15〜20分**になる。
- そこで、件数の数え方と見せ方を分ける。
  - 店は駅に近い順に「駅前（〜300m）」「徒歩圏（〜800m）」「少し歩く（800m〜1km・子連れで15〜20分）」の3段で表示し、1km超は載せない。
  - 配信の基準は「1km以内に3店以上」。ただし**題名・見出しで「駅近」「徒歩圏」と言えるのは、800m以内に3店以上ある面だけ**。それ以外は「徒歩15分圏」などと書く。
  - 店ごとに直線距離と目安の徒歩時間（大人・子連れ）を出す。線路・幹線道路の向こう側は遠回りになる、と注記する（既存の注記を流用）。
- 1kmの効果: 業態3条件で復活できる面が 10面（800m）→ 46面（1km）。全条件では §6 のとおり。

## 5. ページの作り

### 5-1. 通常型（根拠つきの店が1km以内に3店以上）
- 店単位の一覧（店名・住所・距離の段・徒歩時間・根拠の段・公式ページ）。チェーンの一般論の紹介文は出さない。
- FAQ は数えた結果からだけ作る（「◯◯駅で公式にキッズメニューの表示がある店は？」→ 件数と店名）。「全店で〜」「基本〜」などの断定は書かない。
- 構造化データ: `ItemList` の各要素を、チェーン名ではなく**店**（`Restaurant`: 店名・住所 `PostalAddress`・`url`）にする。設備は、根拠の段が店の公式・ブランドの公式の項目だけを `amenityFeature` に入れる。ホットペッパーの店は名前・住所・URLまで。
- 同じ駅の他の条件・近くの駅の同じ条件へのリンクは、配信中の面だけに張る（今と同じ）。

### 5-2. 少数掲載型（1km以内に1〜2店・需要あり）
- 見つかった店をそのまま出し、「公式で確認できたのは◯店」と件数を正直に書く。
- 足りない分を作らない。代わりに、①1〜2km の同じ条件の実在店（距離つき）、②同じ駅の他の条件で店が多い面、③近くの駅の同じ条件、を案内する。
- index のまま残す（需要がある面）。90日ごとに表示実績を見て、表示0が2期続いたら駅トップへ301にする。

### 5-3. 店が0の面（1km以内に0店・需要あり）
- 配信中の6面（羽田空港T3の0〜1歳など）は消さずに作り直す（「この駅の徒歩圏で公式に確認できた店はありません」＋2km以内の実在店＋駅の施設（授乳室など）の案内）。
- 消えた99面（202クリック）は、まず表示の多い上位20面だけをこの型で戻して、28日で表示・クリックを見る。残りは結果を見て決める。
- 0〜1歳・キッズメニューの0店は、店が無いのではなく**根拠のデータが無い**ことが多い（公式店舗検索に項目が無いチェーンが20以上）。根拠の拡充（§8）で埋まる見込みがある。

### 5-4. 雨の日
- 建物の公式台帳 `scripts/station-verify/building-access.json`（新設）に、建物ごとに「駅直結・雨に濡れずに行ける／行けない／記載なし」と原文・URL・確認日を持つ。「直結」と書けるのは「はい」の建物だけ。
- 品川で調べた例: 公式に「駅直結」「雨に濡れずに」とあるのは品川イーストワンタワーだけ。スカイウェイ（品川インターシティ・品川グランドコモンズ・品川グランパサージュ）は「歩行者専用通路でつながる」とあるが屋根の記載が無いので「記載なし」。
- 建物名から3店以上になりうる駅は62駅（配信中24・消えた面12・その他）。確かめる建物は約170棟。**台帳ができるまで雨の日は判定を保留し、配信中の51面は「雨の日」を名乗る理由（直結・屋内）を書かない形にする**（§9 の Phase 0）。

## 7. 凍結記事・内部リンク・サイトマップ・構造化データへの影響

- **凍結記事**: 条件つきの駅リンク（`lib/article-station-link.ts`）を持つ凍結記事は43本。採用案では配信中の面を消さず、凍結記事がリンクしている消えた面（品川・水道橋・新橋の雨の日、下赤塚・高輪ゲートウェイの0〜1歳）はどれも転送のままなので、**リンク先が変わる凍結記事は0本**（試算）。ただし判定の実装を変えるので、PRごとに `check-frozen` の描画層で確かめる。リンク先が動く場合に備えて、凍結slugの駅リンクを判定日まで今の href に固定する仕組み（固定表）を Phase 2 に入れる。
- **関連記事欄・自動リンク**: 記事側は変えない。
- **駅ページ・路線ページからの内部リンク**: 戻した面に、駅トップの「条件で絞り込む」、路線ページの「条件で探す」、同じ駅の他の条件からのリンクが戻る。件数チップの数字は根拠つきの件数に変わる。
- **サイトマップ**: `sitemap.ts` は同じ判定を使うので、戻した面（最大236＋試験20）が載る。`lastmod` はデータの更新日にする（ビルド時刻にしない。9/03 の事故の再発防止）。
- **構造化データ**: 条件ページの `ItemList` を店単位に、FAQ を数えた結果からに変える。Search Console の構造化データのレポートで、公開から2週間エラーを見る。
- **転送**: 戻した面は301を外す（`STATION_COND_DEMAND` の扱いを判定から切り離す）。301を外した面は Cloudflare をパージする（本番の `purge-cf`）。
- **費用（Vercel）**: 条件ページは静的生成（`dynamicParams=false`）のまま。ビルドのページ数は最大+256（いま4,958ページ）。本番ビルドの時間はデプロイ後に確かめる（10/23 に上限45分を超えた前例があるため）。ルート・キャッシュ・middleware は変えない。

## 8. 根拠を増やす（並行）

- 公式店舗検索に設備の項目が無いチェーン（スターバックス・ドトール・丸亀製麺・サイゼリヤ ほか20以上）は、ブランドの公式ページ（キッズメニュー・アレルギー・FAQ）を `chain-facilities.ts` に `scope: 'brand'` で足せるか確かめる。サイゼリヤのお子様メニューなど、全店向けの公式の記載があれば数えられる。
- 店の公式ページを1件ずつ読む調査は、配信中の少数掲載型（94面）の上位から行う。

## 10. 決めたこと（2026-10-28 社長）

1. 配信の基準は「1km以内に3店以上」、「駅近」と書ける基準は「800m以内に3店以上」。
2. 店0の面は、消えた99面のうち表示上位20面だけ試験で戻す。
3. ホットペッパーの店の記載（店が書いたコメント）を、0〜1歳・キッズメニュー・個室の根拠に数える（「店の記載」と明記する）。
4. Phase 0 を先に実装する（判定は変えない）。PR は作るがマージは指示待ち。

## 11. 実装の記録（2026-10-28）

- Phase 0: PR #389・#390・#391（本番済み）。Phase 1: PR #393（データ）。Phase 2: このPR。
- 配信の判定は `lib/station-cond-index.ts` の `stationConditionServeMode`（`isStationConditionIndexable` から呼ぶ）。対象は照合済みの575駅×6条件（ファミレス・回転寿司・焼肉・キッズメニュー・0〜1歳・個室）。雨の日・個人店と、575駅以外の駅は従来の判定のまま。
