# 施設セルフサーブ 技術検証と問題点の洗い出し（デプロイ前の分析）

作成: 2026-09-15
前提: `docs/facility-selfserve-2026-09.md`（構想と段階計画）
方針の確認: 課金は後回し。**まず登録して使ってもらう**。全掲載施設に営業をかける。年内30万PV（ユーザー向け）と並行。
このドキュメントは**実装せず、検証だけした結果**。すべてリポジトリ実測。

## 0. 結論（先に読む）

| 問い | 答え |
|---|---|
| 住所・営業時間がないのが伸びていない理由か | **必要条件だが、それだけではない。そして現状まだ証明できていない。** §1 |
| 住所・営業時間はすぐ入れられるか | **コードは1日。データは1日で終わらない。**820施設分をどこから取るかが律速。§2 |
| 施設セルフサーブは技術的にすぐいけるか | **いけない。今の保存構造のままだと、施設が2人同時に編集すると片方のデータが消える。** §3-1 |

## 1. 「住所・営業時間がないから伸びていない」は本当か

### 正しい部分

施設ページが構造的に不利なのは事実で、それは実測で裏づけられる。

| 項目 | 実数 |
|---|---:|
| 施設ページ | 820（96.5%がindexable） |
| 住所 | **0**（`Spot` 型に `address` フィールドが存在しない） |
| 営業時間 | **0**（`hours` も無い） |
| 電話 | **0** |
| **公式サイトURL** | **108（13.2%）** ← 新発見 |
| 最寄り駅 | 665（81.1%） |
| 設備情報1件以上 | 500（61.0%） |
| 料金1件以上 | 405（49.4%） |
| 画像 | 153（18.7%） |
| 確認記録（verification） | 412（50.2%） |
| 実訪問レポート | 66（8.0%） |
| 駐車場（構造化） | 14（1.7%） |

施設名で検索する人が欲しい「住所・営業時間・写真・電話」を、公式サイト・Googleマップ・いこーよ・じゃらんは全部持っていて、きょうのこは**一つも持っていない**。この状態の `LocalBusiness` が上位に来ないのは自然です。

### 正しくない、あるいは未証明の部分

**(a) 因果が証明されていない。**
`/spot/*` の GSC 実数（imp・CTR・順位）がこのセッションでは取れません（クラウドに GSC の鍵が無い）。「住所を入れたら順位が上がる」を今の手持ちデータで主張できません。

**(b) 住所・営業時間を入れても、施設名の指名検索で公式とGoogleマップに勝つのは難しい。**
指名検索の1位は原則その施設の公式サイトで、2番目以降はGoogleのローカルパック（マップ）が面を占めます。住所を入れて追いつくのは「情報の欠落」という減点の解消で、**加点にはなりにくい**。

**(c) だから住所・営業時間の本当の効き先は、指名検索の順位ではなく次の4つ。** ここを狙う前提で入れるべきです。

| 効き先 | 理由 |
|---|---|
| **エリア・条件一覧の精度** | いま市区町村（`city`/`ward`）粒度しか無く、「渋谷区の授乳室ありスポット」までしか作れない。住所があれば駅・徒歩分・沿線で切れる |
| **AI引用** | ChatGPT経由セッションが週49→240（7週で5倍・`reports/geo-audit-2026-09-02.md`）。AIは住所・営業時間つきの構造化データを好んで引く。**ここが今いちばん伸びている流入** |
| **PV/セッションと回遊** | 1.26 → 1.5 が `docs/strategy-2026-09.md` §3 の式の第4項。行動可能な情報があるページは回遊する |
| **施設に編集させるフック** | 空欄があるほど直したくなる（損失回避）。**セルフサーブの動機そのもの** |

### 提案：入れる前に50件で実験する

`docs/experiments-active.md` の枠組みが既にあるので、それに乗せます。

- 処置群50施設：住所＋営業時間＋電話を入れる
- 対照群50施設：カテゴリ・現在の順位帯・画像有無を揃えて**何も触らない**
- 期間：4〜6週間。判定：imp・CTR・平均順位・AI経由セッション
- ⚠️ 対照群は絶対に触らない（過去2回、凍結記事を触って実験が無駄になった経緯が SKILL.md に記録されている）

**820件に一斉投入する前にこれをやる理由**: 効かなかったときに、820件分の「腐る情報」を抱え込まずに済むから。§2-3 の通り、営業時間は入れた瞬間から腐り始めます。

## 2. 「すぐ入れられる」を分解する

### 2-1. コード変更は本当に小さい（実測ベースで1日）

触るのは5〜6ファイル。既存の設計にそのまま乗ります。

| ファイル | 変更 |
|---|---|
| `lib/spots.ts` | `Spot` 型に `address` / `hours` / `closedDays` / `tel` を追加 |
| `lib/spot-overrides.ts` | `SPOT_TEXT_FIELDS` に4つ追加（このホワイトリストが編集可否を決めている） |
| `app/api/admin/spot-overrides/route.ts` | `sanitizePatch()` に検証を追加（電話の形式・文字数） |
| `app/admin/spots/edit/SpotsEditClient.tsx` | 入力欄を4つ追加 |
| `app/spot/[slug]/page.tsx` | 既に**「基本情報」テーブル（`KkInfoTable`）がある**（L597付近）。行を足すだけ |
| `lib/spot-schema.ts` | `addressLocality` のみ → `streetAddress` / `openingHoursSpecification` / `telephone` へ拡張 |

**設計の型は既にリポジトリの中にあります。** `lib/spot-parking.ts` が答えを持っています:

```ts
exists: boolean | 'unknown';   // ← 「確認できていない」を独立した状態として持つ
hours?: string;                 // 確認できたものだけ書く
sourceUrl: string;              // 一次情報のURL
confirmedAt: string;            // 実際にその生HTMLを見た日
```

そのファイルのコメントに、なぜこの形が必要かが書かれています:

> `exists: 'unknown'` を型として持つ。**これが無いと書き手は必ず「あり」に倒す。**
> 施設固有の断定154箇所のうち **132箇所（86%）に営業時間の記載がなかった**。
> 確定した事実誤り5件のうち**3件が料金**。

**住所・営業時間も同じ形（値＋出典＋確認日＋「未確認」状態）で持つべきです。** 素の `string` で入れると、同じ監査結果をもう一度作ることになります。

### 2-2. データはどこから取るのか（ここが律速）

820施設 × 住所・営業時間。選択肢を全部検討しました。

| 取得元 | 可否 | 問題 |
|---|---|---|
| **Google Places API** | **規約上ほぼ不可** | Google Maps Platform の規約は `place_id` 以外のコンテンツの恒久保存を禁じています。住所を自社DBに保存して表示するのは**規約違反になる可能性が高い**。導入前に規約原文の確認が必須。回避策として都度APIを叩く設計にすると、820ページ×表示回数分の課金と表示要件（Googleの帰属表示）が発生し、SEO目的には使えない |
| **公式サイトから照合** | 可能だが高コスト | クラウドセッションからは**施設公式サイトへの通信が遮断**されている（`docs/strategy-2026-09.md` の環境制約表で実測済み）。ローカル限定。820施設×公式1〜3ページ＝**チェーンDB化と同じ律速**。しかも `officialUrl` が分かっているのは108件だけなので、まず公式URLを探す工程が先に入る |
| **自治体・国のオープンデータ** | **有望・未着手** | 公園209・博物館137・動物園71・水族館57＝**474件（58%）が公共施設寄り**。自治体オープンデータや観光施設データで住所は機械取得できる可能性が高い。ライセンス（CC-BY等）の出典表記が必要。**営業時間は含まれないことが多い**ので住所だけ埋まる |
| **施設本人に入れてもらう** | これが構想の本体 | 量は稼げないが、**営業時間の鮮度を唯一担保できる方法** |

**帰結**: 住所は「オープンデータで474件を機械投入 → 残りと営業時間は施設本人＋実験群の手作業」の二段構えが現実的。**一斉に820件入れる方法は存在しません。**

### 2-3. 入れたら腐る、という別のコスト

`lib/spots.ts` が住所を持たない理由は「変更リスクがあるため」で、これは正しい判断でした。入れるなら、その判断を覆す責任が発生します。

- 営業時間は季節変動・臨時休業・改装で変わる
- 一度入れて放置すると、**1年後には誤情報の山**になる
- `scripts/check-parking-freshness.mjs` と同型の `check-hours-freshness.mjs` が必要（確認日が古い項目を検出して**表示から落とす**）
- **確認日が一定期間より古い営業時間は出さない**ロジックを最初から入れる。後付けにすると誰もやらない

## 3. セルフサーブは「技術的にすぐ」いけるか → いけない

### 3-1. 【重大】保存構造が単一施設の管理者用で、複数編集者に耐えない

`lib/spot-overrides.ts` と `app/api/admin/spot-overrides/route.ts` を読んだ結果、保存はこうなっています:

```
全820施設の上書きデータ = KV の単一キー `spot:overrides` に入った1個のJSON
保存時: 全体を読む → 該当slugを書き換える → 全体を書き戻す（read-modify-write）
```

**問題A：ロストアップデート（データが消える）**
施設Aと施設Bがほぼ同時に保存すると、後に書き戻した方が先の変更を**丸ごと上書きして消します**。運営者1人なら起きませんが、施設が同時に編集する前提では必ず起きます。しかも**消えたことに誰も気づけません**（エラーにならない）。

**問題B：サイズ**
- 現在：上書き済み181施設で **約547KB**（compact。`lib/spot-overrides.json` はpretty印字で1.47MB）
- 1施設あたり約3KB
- 820施設が埋まると **約2.5MB**。住所・営業時間・写真URL・お知らせが加わればさらに増える
- **1回の保存ごとにこの全量を送受信します。** Upstash/Vercel KV の1リクエスト上限はプラン依存なので、**スケール前に自分のプランの上限を確認する必要があります**

**対策（Phase 1の必須工事）**
- 上書きを**slug単位のキー**に分割する（`spot:override:<slug>`）。一覧が必要な箇所はインデックスキーか `SCAN` で持つ
- 保存を read-modify-write から**該当キーだけの更新**に変える（衝突の範囲が1施設に閉じる）
- 移行スクリプトが必要（単一キー → 分割キー）。既存の `sync-spot-overrides-from-kv.mjs` / `push-spot-overrides-to-kv.mjs` も追随して直す
- **運営者レイヤーと施設レイヤーを別キーにする**（出典が混ざると監査が壊れる）

これは1〜2日で終わる工事ですが、**やらずに施設を入れると静かにデータが消えます**。

### 3-2. 【重大】書き込みAPIの認可が、施設には使えない

現在の保護は2枚だけです:

```ts
if (process.env.NODE_ENV === 'development') return { ok: true };
if (process.env.ALLOW_ADMIN_EDIT === '0') return { ok: false };
const ref = req.headers.get('referer') || '';
if (!/\/admin\//.test(ref)) return { ok: false, reason: 'invalid referer' };   // ← これだけ
```

- **referer はクライアントが自由に付けられる**ので、単独では認可になりません。今は `middleware.ts` の Basic 認証（`/admin` 配下のみ）が前段にあるので実害はありません
- **この API を施設向けに再利用してはいけません。** 再利用すると referer チェックが唯一の関門になり、誰でも任意施設の情報を書き換えられます
- 必要なのは「ログインしているか（認証）」＋「**その人がその slug の所有者か**（認可）」の2つ。後者が本質で、既存コードに概念自体がありません
- 施設用は別パス（例 `/facility/*` と `/api/facility/*`）にします。`middleware.ts` の matcher は `['/admin/:path*', ...]` なので `/facility` は Basic 認証にかかりません（＝自前で守る必要がある）

### 3-3. オーナー確認が87%の施設で成立しない ← 計画の修正が必要

前のドキュメントで「公式ドメインのメールなら自動承認」と書きましたが、**実測したら前提が崩れました**。

| カテゴリ | 施設数 | `officialUrl` あり |
|---|---:|---:|
| 飲食店 | 114 | **100** |
| 屋内遊戯施設 | 141 | 6 |
| 博物館・科学館 | 137 | 1 |
| 公園 | 209 | 1 |
| 動物園 | 71 | **0** |
| 水族館 | 57 | **0** |
| 遊園地 | 58 | **0** |
| 牧場 | 16 | **0** |
| 観光スポット | 17 | **0** |
| **合計** | **820** | **108（13.2%）** |

**こちらが公式ドメインを知らないので、ドメイン照合で本人確認ができません。**

**修正案**:
1. **先に `officialUrl` を埋める**（公式URLは住所より探すのが速く、オープンデータでも取りやすい）。これは**オーナー確認の前提工事**であり、同時に §1 の「公式サイトで最新情報を確認」導線の改善にもなる（今は13%の施設でしか出ていない）
2. 公園・博物館・動物園は**自治体・指定管理者が運営**しており、「公式ドメインのメール」を持つ担当者が個人単位で存在しないことが多い。ここは最初から**手動審査前提**で設計する（自動承認にこだわらない）
3. 当面は **claim申請 → 人力で公式サイトの窓口に照会 → 承認** で回す。件数が少ないうちはこれで足りる（＝Phase 0 の設計が正しい）

### 3-4. ログイン用のメール送信手段が無い

`.env.example` を確認した結果、設定されているのは `NEXT_PUBLIC_TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` のみ。**メール送信プロバイダの設定が一つもありません**（Resend・SES・SendGrid・SMTP いずれも無し）。

マジックリンク認証には次が必要です:
- 送信プロバイダの契約（Resend等）
- 送信ドメインの SPF / DKIM / DMARC 設定（未設定だと施設側のメールサーバに弾かれる。**B2B相手なので到達率が致命的**）
- 到達しなかった場合の代替手段（運営者が手動で発行するワンタイムリンク）

**見積りへの影響**: 認証は「Auth.jsを入れる」では終わらず、ドメイン認証の設定と到達率の確認が入ります。

### 3-5. 反映の速さ（これは既に解決済み）

心配なさそうな点も記録しておきます。編集が画面に出るまでの経路は既に整備されています。

- `app/spot/[slug]/page.tsx` は `revalidate = 86400`（24時間ISR）
- CFエッジは `s-maxage=3600`
- **保存時に `revalidateTag` + `revalidatePath` + `purgeCfUrls(['/spot/<slug>', '/', '/spots', '/ranking'])` を実行**（`route.ts`）→ 数秒で反映

⚠️ ただしパージ対象に **`/station/*`・`/area/*`・`/category/*` が入っていません**。施設が施設名や写真を変えても、駅ページ・エリアページには最大1時間（CF）＋ISR分だけ古い表示が残ります。施設本人が「直したのに変わってない」と問い合わせてくる箇所なので、パージURLの拡張が必要です。

## 4. 営業を始める前に潰すべき問題（2件）

### 4-1. 【要対応】連絡先が30件しか無い。846件ではない

`docs/outreach-full-688.csv`（846行）をパースした結果:

| 列 | 埋まっている行数 |
|---|---:|
| 施設名・エリア・市区町村・掲載URL | 846 |
| **公式サイト** | **0** |
| **問い合わせ方法** | **0** |
| **Instagram** | **0** |
| **メディア窓口** | **0** |

連絡先が入っているのは `docs/outreach-pilot-30.csv` の**30件のみ**（こちらは公式サイト・プレス窓口・Instagram・所感まで埋まっている良質なリスト）。

**「まず全施設に営業をかける」には、816件分の窓口調査が先に必要です。** そしてこの調査は:
- クラウドセッションからは**施設公式サイトに到達できない**（ローカル限定作業）
- 1件3〜5分でも **40〜70時間**
- **年内30万PVのためのチェーン公式照合と、同じリソース（ローカル作業時間）を食い合います** ← 並行の本当の衝突点はここ

**現実的な順序**: pilot-30 で先に反応率を測る → 反応が良ければ Tier A から100件ずつ窓口調査。全846件を先に揃えない。

### 4-2. 【要対応】営業メールに送る掲載URLのうち98件が死んでいる

CSV の846件の掲載URLから slug を抽出して現存データと突合した結果:

- 現存する slug: **748件**
- **存在しない slug: 98件**（リダイレクト済み・削除済み・URL変更）

「貴施設のページ、もう公開しています」という営業で**リンクが404になるのは最悪のパターン**です。送信前に突合スクリプトを回して、死んでいる98件を除外または最新URLに差し替える必要があります（`lib/spot-redirects.ts` に移行先がある分は救えます）。

### 4-3. 【法務・要確認】一斉営業メールは特定電子メール法の対象になりうる

広告宣伝を目的とするメールは、法人宛でも次が必要です:
- 原則オプトイン（事前同意）。ただし**名刺交換等の例外**あり
- 送信者の氏名・名称、住所、**受信拒否の通知先**の表示
- 受信拒否した相手への再送信の禁止

「無料掲載のご案内」は広告宣伝性を帯びうるので、**メール文面に送信者情報と配信停止方法を入れる**。これは文面テンプレートに1回入れれば済む作業です（`docs/outreach-messages.md` の改訂）。フォーム送信や電話は対象外。

## 5. まだ誰も見ていない問題（3件）

### 5-1. 【重要】「掲載を取り下げてほしい」と言われる導線を同時に開くことになる

現在の820施設は、公開情報をもとに無許諾で紹介しています（適法だが、施設の同意はない）。営業をかけ、マイページを開けば、**必ず一定数が「載せないでほしい」と言ってきます**。

**今、それに対応する仕組みがありません。**
- `lib/spot-closed.ts` は**閉館専用**（noindex＋閉館バナー）。「施設の要望による非掲載」とは意味が違う
- 閉館扱いにすると「閉館しました」と表示されるので、**営業中の施設に使うと重大な誤情報になります**
- 必要なのは `SPOT_DELISTED`（noindex＋一覧から除外＋ページは410/404、理由は非公開）という別の状態

**営業を始める前にこれを用意すべきです。** 取り下げ要求に即応できないと、その施設との関係も評判も失います。

### 5-2. 施設が投稿した写真の権利

施設担当者が「自社の写真」としてアップしたものが、実際には委託カメラマンや第三者の著作物であるケースは普通に起きます。媒体側が公開した時点で責任が生じます。

- 施設向け利用規約に**権利の表明保証**（第三者の権利を侵害しないこと、利用許諾の範囲、人物の写り込みの承諾）を入れる
- 削除申立てへの窓口と対応フローを決める
- `imageKind`（`実写` / `提供` / `streetview` / `UGC` / `イメージ`）と `imageCredit` が既に型にあるので、**施設提供は `提供` ＋ `imageCredit` を必須にする**（既存の画像ポリシーにそのまま乗る）

### 5-3. 施設担当者の個人情報を持つことになる

氏名・メール・電話を保持するので:
- プライバシーポリシーに取得目的・利用範囲・第三者提供の有無を追記
- KVに平文で持つ範囲を最小にする（認証に必要な情報だけ）
- 課金を始める段階で特定商取引法の表記が追加で必要（今回は対象外）

## 6. 並行できるか（30万PVとの両立）

**結論：並行できます。ただし衝突点が1つあり、そこだけ意識的に配分が必要です。**

| リソース | 衝突 |
|---|---|
| コード実装の時間 | 衝突する（同じ1人）。ただし施設側は §3 の工事が中心で、SEO施策とは別ファイル |
| **ローカルでしかできない調査時間** | **強く衝突する。**施設の窓口調査（§4-1）と、チェーン公式の照合（30万PVの律速）が同じ枠を取り合う |
| GSC分析 | 衝突しない。むしろ共通（`/spot/*` の実数は両方に必要） |
| 記事執筆 | 衝突しない |

**配分の提案**: ローカル作業の枠を、しばらく **チェーン公式照合7：施設窓口調査3** で置く。施設側は pilot-30 の反応率が出るまで枠を増やさない（増やす根拠がまだ無い）。
