# 本番ビルドの静的生成が45分の上限に迫る原因（2026-10-23）

## 結論

1. **遅い区間は記事ページ（/article/[slug]・約1,407枚）だった。** 原因は、記事一覧を返す `getAllFileArticles()`（`lib/articles.ts`）がキャッシュを持たず、呼ばれるたびに全1,407本のmdを読み直して解析していること。記事ページ1枚の描画で何度も呼ばれるため、記事が増えるほど二乗で遅くなる。
2. **KV（Upstash）の待ちは主因ではない。** KVに一切つながらない手元のビルドでも、同じ記事ページの区間で同じように遅くなった。
3. **対処案A（推奨）**: `getAllFileArticles()` の結果を、本番ビルドと本番実行時だけ1プロセスにつき1回だけ読む形にする（10行程度の変更）。手元のビルドで静的生成が **7分35秒〜9分43秒 → 2分4秒**（約−73〜79%）になった。記事とスポットの全2,243ページで、title・構造化データ・metaタグ・リンク・表示テキストが変更前と一致した。
4. 実装PRは未作成（社長の承認後）。Vercel設定・ISR・ルートは変えない案なので、費用は下がる方向。

## 遅い区間の特定（手元・10コア・KVなし）

生成されたHTMLの書き込み時刻をルート別に30秒単位で集計した（元のままのビルド）。

| 経過 | 生成されたページ |
|---|---|
| 0〜30秒 | 駅×条件 1,468・駅 630・イベント 262・スポット 233 |
| 30〜120秒 | スポット 603・プラン 352・記事 208 ほか |
| 120〜450秒 | **記事だけ**（30秒あたり約100枚） |

駅（約2,100枚）は30秒、スポット（約836枚）は約90秒で終わる。記事は手元でも1枚あたり約2〜3秒の計算がかかっていた。

## 原因

- `getAllFileArticles()` は呼ばれるたびに `content/articles/` の全mdを `readFileSync` し、`gray-matter` で frontmatter を解析して並べ替える。手元で1回約0.12秒（初回0.16秒）。
- 記事ページの描画からは、関連記事（`getRelatedFileArticles` 内で2回）、姉妹記事チップ、シリーズ・クロスリンク、タグ、記事ページ本体（2か所）などから繰り返し呼ばれる。短縮できた時間から逆算すると、1ページあたり約18〜25回分（推定）。
- 記事数 × 1ページあたりの呼び出し回数 × 記事数、の形で効くため、記事が増えるほどビルドが二乗で遅くなる。9月以降の記事の大量追加でビルドが上限に近づいた。

## KVの読み込み（副次的な所見）

- スポットのページは、口コミ・評価・投稿画像をKVから順番に3回読む（キャッシュなし）。評価のキーが無いスポットでは、ビルド中にKVへ評価を書き込む（`computeRating` の `kvSet`）。
- KVクライアント（@upstash/redis）は通信エラー時に最大5回再試行し、待ちは合計約4.3秒になる。
- ただしKVなしの手元ビルドでもスポットは約90秒で終わっており、全体への影響は記事ページより小さい。今回の対処には含めない（必要なら別PRで、3回の読み込みを並列化する）。

## 対処案

| 案 | 内容 | ビルド時間の見込み | 費用への影響 | SEO・表示への影響 | 実装の大きさ |
|---|---|---|---|---|---|
| **A（推奨）** | `getAllFileArticles()` の結果を `NODE_ENV === 'production'` のときだけプロセス内に保持し、2回目以降は複製を返す（devでは毎回読む＝md編集が即反映） | 手元で静的生成 −73〜79%。Vercelでは静的生成 約25〜43分 → 推定8〜12分（4コアで手元の約4〜5倍として） | ビルドCPU（Vercel費の最大要因）が減る。ISRの再生成も軽くなる。増える要素なし | 出力は変わらない（2,243ページで一致を確認） | 約10行・lib/articles.ts のみ |
| B | 記事ページの事前生成を需要のある記事に絞り、残りを初回アクセス時のISRに回す | 記事の本数に比例して短縮 | 実行時の関数呼び出しが増える（費用ガードの対象・72時間の実測突合が必要） | 初回アクセスだけ遅くなる | 中 |
| C | ビルドマシンの増強（Enhanced Builds） | 短縮 | 月額が増える | なし | 設定のみ（有料） |

Aだけで上限まで十分な余裕ができる見込み。B・Cは不要と見る。

## 案Aの差分（実装PRでそのまま使う想定）

```ts
// lib/articles.ts
let allFileArticlesCache: FileArticleMeta[] | null = null;

export function getAllFileArticles(): FileArticleMeta[] {
  // 本番ビルド・本番実行時は content/articles が変わらないので、1プロセスで1回だけ読む。
  // 呼び出し側が並べ替えても保持分が崩れないよう、毎回配列の複製を返す。dev は毎回読む。
  const memo = process.env.NODE_ENV === 'production';
  if (memo && allFileArticlesCache) return allFileArticlesCache.slice();
  const files = readArticlesDir();
  const metas: FileArticleMeta[] = files.map((filename) => { /* 現行どおり */ });
  const sorted = metas.sort((a, b) => (a.publishedAt < b.publishedAt ? 1 : -1));
  if (memo) allFileArticlesCache = sorted;
  return sorted.slice();
}
```

- 呼び出し側が記事メタのオブジェクト自体を書き換えている箇所は見つからなかった（配列の並べ替え・絞り込みのみ）。
- KVの記事上書き（`getAllFileArticlesWithOverrides`）は別の経路で、影響しない。
- scripts/ の検査（check-frozen など）は NODE_ENV が production でないため従来どおり。

## 検証のしかた（実装PRで行うこと）

1. 手元で変更前後のビルドを取り、記事・スポットの全ページで title・構造化データ・meta・リンク・表示テキストが一致すること（今回の手順を再実行）。
2. マージ後の本番ビルドで、Vercelのビルド時間と静的生成の所要時間を記録し、この報告の見込みと突き合わせる。
3. 凍結ガード（check-frozen）を通す。

## 調べ方

- Vercel のビルドログ4本（`vercel inspect <url> --logs`）とエラーコード（`vercel api /v13/deployments/<url>`）。
- 手元（Apple Silicon 10コア・Node 24・KV/microCMSの接続情報なし）で `next build` を3回（元のまま2回・案A相当1回）。生成されたHTMLの書き込み時刻をルート別に集計。
- 案A相当の出力と元のままの出力を、記事1,407＋スポット836ページで比較。ビルドIDとスクリプトのハッシュを除くと、4,486ファイル中4,410が完全一致、残り76（38ページ分）は埋め込みデータの流し込み順だけが違い、title・構造化データ・meta・リンク・表示テキストは全2,243ページで一致。
