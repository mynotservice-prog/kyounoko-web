### 専業競合: machikurabe.jp（合同会社AsoBi）

ほぼ全クエリに顔を出す唯一の専業。出典明示・確認日記載は誠実（「2026年3月確認」）で侮れない。ただし実測した弱点:
- 比較表が**主要10区市どまりで23区全部を並べていない**（粒度で勝てる）

## (b) DBスキーマ案（chain-facilities.ts 踏襲）

新規ファイル想定: `lib/ward-benefits.ts`（単一データソース）。
chain-facilities との差分は2点: **セル単位で sourceUrl + verifiedAt を必須にする**（制度は区ごとに改定時期が違うため、チェーンのようなレコード単位のverifiedAtでは事故る）。**「公式に記載なし」を表現する status を持つ**（writing-rules §4「あるともないとも書かない」の構造化）。

```ts
/** 制度キー（第一波。後から追加可能） */
export type BenefitKey =
  | 'birthGrant'        // 出産費用助成・出産祝い金（区独自）
  | 'birthGift'         // 誕生祝い品（買物券・記念品）
  | 'diaperDelivery'    // おむつ定期便・0歳児見守り事業
  | 'medicalExtra'      // 医療費助成の区独自上乗せ（都制度との差分のみ）
  | 'schoolLunch'       // 給食費（無償化の対象範囲・所管の注記）
  | 'daycareDiscount'   // 保育料の区独自減免（都制度との差分のみ）
  | 'housingSupport'    // 子育て世帯向け家賃補助・住み替え支援
  | 'babysitterSupport';// ベビーシッター利用支援（都事業の区別実施状況）

export const BENEFIT_LABELS: Record<BenefitKey, string> = { /* 表示名 */ };

export type BenefitValue = {
  /** yes=区独自制度あり / no=公式が「なし」または都・国制度のみ /
      partial=条件付き / unknown=公式に記載を確認できず（→UIで確認導線を出す） */
  status: 'yes' | 'no' | 'partial' | 'unknown';
  /** 公式文言ベースの要約（例:「上限31万円（1子・2023-04-01時点）」）。捏造防止のため公式の数字以外書かない */
  summary: string;
  /** 比較ソート・「最大◯円の差」集計用。公式に金額明記がある場合のみ */
  amountYen?: number;
  /** 所得制限・居住年数要件・申請期限など */
  conditions?: string;
  /** 出典URL（区公式または都公式のみ。まとめサイト不可）— 必須 */
  sourceUrl: string;
  /** 出典ページ名（リンク切れ時の再探索用） */
  sourceTitle: string;
  /** このセルを一次情報で確認した日 — 必須。値を変えたら必ず更新 */
  verifiedAt: string; // YYYY-MM-DD
  note?: string;
};

export type WardBenefits = {
  key: string;          // 'minato'（区コード13103も併記推奨: jisCode）
  name: string;         // '港区'
  jisCode: string;      // '13103' 全国地方公共団体コード（将来の市部拡張・オープンデータ照合キー）
  officialKosodateUrl: string; // 区の子育て支援トップ（発リンク先）
  items: Partial<Record<BenefitKey, BenefitValue>>; // 未調査キーは省略=表示しない
};

export const WARD_BENEFITS: WardBenefits[] = [ /* 23区 */ ];
```

設計判断のメモ:
- **`unknown` と キー省略を区別する。** 省略=未調査（表に出さない）、unknown=調査したが公式に記載がない（表に「公式記載なし・区に確認」と出す）。writing-rules §4 の直訳。
- **medicalExtra / daycareDiscount は「都制度との差分」だけ持つ。** 全区共通の土台（マル乳/マル子/マル青、都の第1子保育料無償化）はDBに複製せず、ハブ記事の冒頭で都公式へリンクして説明する。差分だけ持てば更新面積が23分の1で済む。
- 検証スクリプトを同時に用意する（実装時）: 全 sourceUrl の HTTP 200 チェック＋verifiedAt が閾値（例: 370日）超のセルを警告。`scripts/check-cross-article-facts.mjs` の隣に置く。

## (c) ページ構成案（IA・カニバリ回避）

### 構造: 「制度軸ハブ」×「区軸ページ」の2軸。すべての表はDB駆動

```
[制度軸ハブ]  /article/tokyo-23ku-shussan-iwaikin-hikaku 等（制度ごとに1本）
   └ 23区×1制度の全区比較表（DB自動生成）＋「最大◯円差」等の集計＋FAQ
[区軸ページ]  /article/kosodate-shien-minato 等（区ごとに1本）
   └ 1区×全制度の一覧表（DB自動生成）＋区の特色＋引っ越し導線
[親ハブ]      /article/tokyo-23ku-kosodate-shien-hikaku（1本）
   └ 頭クエリ「23区 子育て支援 比較/手厚い区」を受け、制度軸ハブへ配分
```

### カニバリ回避（メモリ「1クエリ1ページ独占」原則の適用）

- **クエリ所有権を軸で分ける**: 「23区 出産祝い金 比較」→制度軸ハブ、「港区 子育て支援」→区軸ページ、「23区 子育て支援」→親ハブ。titleに他軸の語を混ぜない（制度軸ハブのtitleに特定区名を入れない、区軸ページのtitleに「比較」「ランキング」を入れない）。
- **既存の23区系3本はすべて noindex:true を確認済み**（tokyo-23ku-family-score-ranking-2026 / tokyo-23ku-family-friendly-area-rankings-3 / tokyo-line-family-friendly-ranking）。現状カニバリなし。ただし本面の公開時に「復活させて親ハブから独自データ枠としてリンク」か「noindex維持」かを決める。**同時にindex化すると「手厚い区/住みやすい区」でカニバるので、親ハブ公開後に片方だけ**。
- 区軸ページは「〇〇区 子育て支援」の指名系を狙うが、区公式が1位固定の前提。**公式が答えない「他区との比較・引っ越し判断」を独自価値の柱に置き、metaにもそれを書く**（公式の複製ページにしない）。

### 記事表示の実装方針（chain-facilities踏襲）

- チェーン記事の判定ボックスと同様、記事slug→DBを引いて比較表・判定ボックスを差し込む。md側に手書き表を持たない（不整合と鮮度切れの構造的排除）。
- 各表の直下に「確認日: セルごとの verifiedAt の最古値」＋「最新は各区公式でご確認ください」＋区公式への発リンクを自動表示。

## (f) 不動産アフィ導線案

前提の実測: **repoに不動産アフィの既存実装はゼロ**（lib/components を grep 済み）。SUUMO・HOME'S(LIFULL)の資料請求/賃貸系プログラムはバリューコマース・A8等にあるが**未提携＝提携申請が先行タスク**（承認に日数がかかるため、Q4前半のデータ収集と並走で申請しておく）。

導線設計（既存のVC CTA基盤 `buildVcDeepLink` 方式を流用）:

| 配置面 | 導線 | 意図 |
|---|---|---|
| 区軸ページ末尾＋中盤 | 「〇〇区の賃貸を子育て条件で探す」→ SUUMO/HOME'S の区×間取り検索結果に深リンク | 「〇〇区 子育て支援」を調べる人の相当数が引っ越し検討層。**検索結果着地**（単品でなく一覧に落とす楽天アフィの実証原則をそのまま適用） |
| 家賃補助ハブ(7) | 補助制度の表の直下に「補助対象になる物件を探す」CTA | 制度→物件の自然な次アクション |

## (g) リスク

1. **コールドスタート（最重要）**: 自治体語彙0.1%＝既存トピック権威が効かない。既存の勝ち面（チェーン×子連れ）とテーマが遠く、内部リンクの後押しも弱い。緩和策: (i) 既存の区名記事（shitsunai-asobi-itabashi 等の室内遊び×区シリーズ）と区軸ページを相互リンクして区エンティティの束を作る (ii) カナリア18本で見切る撤退ラインを事前に固定（(e)参照） (iii) noindex中の23区独自データ記事の復活で面に厚みを足す。
2. **YMYL性**: 医療費・給付金は金銭・公共制度でGoogleの品質要求が高い。E-E-A-T が薄いと圏外に置かれ続ける可能性。緩和策: セル単位の出典URL+確認日（machikurabe が持たない粒度）、区公式・都公式への発リンク、編集方針ページからの参照、集計・断定は amountYen が取れたセルのみで行う。
3. **公式との差分事故（このサイトの前科の型）**: 1,109本監査・捏造見出し4系統の事故はすべて「公式にない数字を書いた」ことから始まった。制度情報は改定が4月に一斉に来るため、**放置すると184セルが同時に古くなる**。緩和策: (b)の unknown status＋セル単位 verifiedAt＋URL 200監視スクリプト＋4月更新タスクの事前予約＋「summaryは公式文言の写し以外書かない」規律。品川区の実例（おむつ定期便の実態は見守り事業）のとおり、**制度名の字面から内容を推定しない**。
4. **専業競合 machikurabe.jp**: 出典明示・確認日つきで同じ土俵にいる。全国1,741自治体を標榜。緩和策: 23区の全区×セル単位出典という粒度、外食・おでかけ既存面との回遊（machikurabe にはない生活動線）、区軸ページの「公式が答えない比較視点」。
5. **SERPの構造リスク**: 給食費のように**制度が収束すると比較クエリ自体が消える**（23区給食費は比較価値が既に消滅済みと今回実測）。医療費も差分縮小トレンド。緩和策: 「差がある制度」（出産助成・祝い品・住宅支援）に投資を寄せ、「差が消えた制度」は直答1本の低コスト運用にとどめる。
6. **収益仮説の不確実性**: 不動産アフィ提携が承認されない/単価が想定より低い可能性。緩和策: 提携申請を先行させ、承認結果をQ4後半の公開判断の入力にする（未承認ならAdSense前提のRPMで面の優先度を再評価）。
